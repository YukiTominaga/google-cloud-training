# 仕様書フォーマット規約 (`specs/<機能名>.md`)

本プロジェクトにおける仕様（`specs/`）は「唯一の正（北極星）」であり、コードは仕様から再生成できる使い捨てのものとして扱います。
すべての機能仕様書 `specs/<機能名>.md` は以下の5つの必須セクションで構成してください。

---

## 1. 背景
なぜこの機能が必要なのか、その動機と背景を記述します。
後続の実装者や検証者が背景・意図を理解した上で次の手順を自律的に推論・判断できる程度の解像度で記載してください。

## 2. 技術設計
実装の詳細な前提条件と制約を定義します。以下の項目を必ず含めてください。
- **ツールのシグネチャ**: 関数名、引数の型ヒント、戻り値の型
- **戻り値の dict 構造**: 成功時・失敗時それぞれの辞書キーと値の構造
- **失敗時の振る舞い**: 外部コマンド不在、非ゼロ終了コード、タイムアウト等のエラーハンドリング方針
- **呼び出す外部コマンド**: 実行する CLI コマンド（例: `gcloud config get-value project`）や外部プロセス
- **セキュリティ制約**: `shell=True` の禁止、タイムアウトの必須化、シークレット情報の除外、入力サニタイズ等の防御策

## 3. バージョン固定
仕様策定時点で動作確認した、または前提とする実際のパッケージバージョンを明記します。
- Python（例: `3.11.18`）
- `google-adk`
- `pytest-bdd`
- その他機能で利用・追加する依存パッケージ

依存パッケージを追加・更新した場合は、必ずこのセクションも更新してください。

## 4. シナリオ (Gherkin)
pytest-bdd で直接実行可能な Gherkin 記法（Feature / Scenario / Given / When / Then / And）で記述します。
`tests/features/<機能名>.feature` と**一言一句同一の文言**を維持してください。

### シナリオ作成の必須要件
各シナリオには必ず連番（`Scenario 1: ...`, `Scenario 2: ...`）を付与し、以下の観点を**必ず各1つ以上**含めてください：
1. **正常系**: 期待通りの入力および環境で正しく処理が成功するケース
2. **失敗状態**: 依存コマンドの失敗、非ゼロステータス、タイムアウト等の異常終了ケース
3. **エッジケース**: 空文字、未設定状態、存在しないリソースなど境界値のケース
4. **セキュリティ**: 不正な入力値、パラメータインジェクション、機密情報漏洩リスクに対する防御ケース

## 5. 決定の記録
実装や設計の過程で行った判断・設計変更・トレードオフを日付とともに記録します。仕様を更新するたびに追記してください。
- 形式例:
  - `YYYY-MM-DD`: <判断内容と理由>
